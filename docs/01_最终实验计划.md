## 0. 一句话

用 SRA-Bench 把 BM25、Dense、Dense+Reranker 三条基线跑齐，先在 100 条 query 上建立可复现的失败分类并测标注一致性，再在 200 条 query 上估计 Functional Mismatch 的占比和排序错误率。只有占比、一致性、可区分性三项同时过线，才做免训练的功能证据重排。

### 1.1 V100 适配（2026-11-20 实测）

服务器 `V100 服务器`，Ubuntu 22.04，20 核，226G 内存，4 张 V100-SXM2-32GB。系统 Python 3.10，但 `safe-draft` conda 环境已有 Python 3.11.18 + torch 2.6.0+cu124 + numpy 2.4.6，和 11 月复现的版本一致。用这个环境建了一个独立 venv，只装 `sentence-transformers==5.5.1` 和 `xformers`，不动别人的环境。

已经确认的四个限制：

| 限制 | 实测情况 | 处理 |
|---|---|---|
| 不支持 BF16 | SM 7.0 没有原生 BF16；模型 config 默认 bf16 | `encoder.py` 按算力自动选 dtype，SM < 8 用 FP16 |
| SDPA 走 math 后端 | Qwen3 是 GQA（16 query 头 / 8 KV 头），V100 的 fused 内核不接受，8k 就 OOM | 关闭 GQA SDPA 路径，先展开 KV，再强制 memory-efficient 后端 |
| 没有 FlashAttention | 只支持 SM 80–90 | 用 xformers / memory-efficient SDPA 代替 |
| 上下文长度 | 32k 时 math 后端要 128G 显存 | 实测语料 p99 约 9,970 token，1.9% 超过 8k；主实验用 `max_seq_length=8192`，`doc_batch=4` |

其他环境事实：

- Qwen3-Embedding-0.6B 已经缓存在 `~/.cache/huggingface/hub`，revision 正好是 `97b0c614...`，不需要联网下载。
- 服务器访问 HuggingFace 超时，但 `hf-mirror.com` 和 ModelScope 可通。新模型用镜像下载。
- 根分区只剩 9.1G。核心检索实验（venv + 模型 + 语料 + embedding + 结果）大约 6–7G，够用；Qwen3-4B 的 8G 权重放不下，所以 E7 默认不在 V100 上做。
- 没有 vLLM，也没有 `nvcc`；PyTorch wheel 自带 CUDA runtime，不影响推理。

实测吞吐：8k 长度、batch 4 时显存峰值约 5.9G；全量 26,262 篇编码预计 3–4 小时，单卡跑一次即可，缓存后续复用。

2026-11-20 的 G0 复现结果：

| 方法 | V100 8k R@10 | 11 月 4090 32k | 差异 |
|---|---:|---:|---:|
| Dense | 66.04 | 66.09 | -0.05 |
| SkillSight | 86.07 | 86.13 | -0.06 |

两项都在 ±0.5pp 内，8k 截断没有改变结论。机制侧也对得上：背景子空间秩 2，解释方差 93.36%，Otsu IDF 阈值 5.5999，通用 token 2,791 个。

分任务有一个必须记住的现象：SkillSight 在 logicbench（35.39→69.21）、toolqa（50.21→91.54）、bigcodebench（55.94→76.68）上大幅提升，但在 champ（62.94→58.98）和 medcalcbench（99.36→99.00）上略低于 Dense。最强基线不是逐任务最强，后面所有失败分析和方法对比都必须分任务报。

## 2. 研究问题与可证伪假设

| 编号 | 问题 | 主要证据 |
|---|---|---|
| RQ1 | BM25、Dense、Dense+Reranker 在 SRA-Bench 上各是什么水平 | R@1/5/10、MRR、nDCG@10、分任务结果 |
| RQ2 | 现有方法的失败由哪些原因造成 | 100 条 pilot 的分类分布与 κ |
| RQ3 | Functional Mismatch 占失败的多大比例，现有 retriever 能否区分主题相关与功能相关 | 200 条验证集的占比、FPER、分数间隔 |
| RQ4 | 显式功能证据能否改善排序 | 只在 G2、G3 都通过后做 |

四个假设，每个都带判定线：

| 假设 | 操作化指标 | 支持标准 | 不支持时的处理 |
|---|---|---|---|
| H1 单 gold 低估了检索性能 | FVA（Functionally Valid Alternative，功能等价替代）占 Dense 失败 query 的比例；`R@5_gold` 与 `R@5_gold∪FVA` 的差 | FVA ≥ 10%，调整后 R@5 提升 ≥ 3pp | 把 FVA 降为描述性统计，不作为主结果 |
| H2 Functional Mismatch（主题相关但功能不满足）是主要失败原因之一 | `P(FM \| fail)`；FM 对 invalid pair 的占比 | `P(FM \| fail)` ≥ 25%，Wilson 95% 下限 ≥ 15% | <10% 走 Stop Rule A；10–25% 降为次要章节 |
| H3 现有 retriever 不能区分主题相关与功能相关 | Functional Pairwise Error Rate（FPER）；valid 与 FM 的分数间隔 | Dense FPER ≥ 25%，最强基线 ≥ 15%，间隔 z < 0.5 | 全部 <10% 时停方法，转测量与 FVA 方向 |
| H4 功能证据能改善排序 | 功能分数的 pairwise accuracy；R@10 增益；控制特征增益 | pairwise ≥ 65%，R@10 ≥ +2.0pp 且配对 bootstrap 95% CI 不含 0，控制特征 ≤ +0.5pp | 只报诊断与阴性结果，不硬做方法章 |

另有一个诊断，不单独设假设，但会决定分析口径：

> **任务域混淆诊断**：把候选池限制到 gold 所属任务族，算 oracle R@10。如果比全池高 20pp 以上，说明失败主要来自跨域路由，FM 分析必须限定在同任务族内部，否则会把“域不匹配”误写成“功能不匹配”。

## 3. 评测协议（E0，先冻结再跑）

### 3.1 候选池与相关性

- 候选池：26,262 个 skill，全量，不做任务过滤。所有方法共用同一个池。
- gold：沿用数据集 `skill_annotations`。多 gold 任务按集合计算 recall，不改成单 gold。
- 额外相关：标注得到的 Functionally Valid Alternative（FVA）只在标注子集上使用，不反写回全量评测。
- query 文本原样使用；`eval_data.answer` 只作为标注时的参考，不进入检索。

### 3.2 数据划分

先跑 Dense，得到每条 query 的 `gold in top-5` 结果，再按任务分层抽样。

| 任务 | 查询数 | gold 数/条 | Pilot 100 | Validation 200 |
|---|---:|---:|---:|---:|
| theoremqa | 747 | 1 | 14 | 28 |
| logicbench | 760 | 1 | 14 | 28 |
| medcalcbench | 1,100 | 1 | 20 | 41 |
| toolqa | 1,430 | 1 | 26 | 53 |
| bigcodebench | 1,140 | 2–6 | 21 | 42 |
| champ | 223 | 1–5 | 5 | 8 |
| 合计 | 5,400 | | 100 | 200 |

- Pilot：每个任务内抽 70% Dense 失败 query + 30% 成功 query。
- Validation：每个任务内抽 80% 失败 + 20% 成功。
- 抽样种子固定为 `20261120`。
- 300 条已标注 query 从最终 test 中剔除，test 为剩余 5,100 条。
- Validation 内部的 200 条再分：120 条用于方法设计与 λ 选择，80 条作为方法评估的 held-out。划分在 W7 冻结。

抽样是 case-control 设计，所以失败内部的占比可以直接用，全体占比必须按任务权重和真实失败率回加权：

```
P(FM) = Σ_t w_t · P(fail | t) · P(FM | fail, t)
w_t = N_t / 5400
```

报告时必须同时给出 `P(FM | fail)` 和回加权后的 `P(FM)`，不能只报前者。

H1 的 adjusted R@5 只在标注子集上做配对比较，即同一批 query 的 `R@5_gold` 与 `R@5_gold∪FVA` 之差，不把子集绝对值当成总体 R@5。样本里失败 query 被故意放大，绝对值不可直接外推。

### 3.3 指标定义

| 指标 | 定义 | 用在哪 |
|---|---|---|
| R@K | TopK 与 gold 的交集大小除以 gold 大小，取 query 均值 | 全量 5,400，主指标 R@10 |
| MRR | 第一个有效 skill 的排名倒数均值 | 全量 |
| nDCG@10 | gold 增益 2，FVA 增益 1，invalid 增益 0 | 标注子集 |
| adjusted R@K | 把 FVA 并入相关集合后的 R@K | 标注子集，H1 |
| FVA rate | 无 gold 但 top-5 内有 FVA 的 query 比例 | 标注子集，H1 |
| `P(FM \| fail)` | 失败 query 中主因为 FM 的比例 | 验证集，H2 |
| FM pair share | invalid pair 中 semantic=2 且 coverage=0 的比例 | 验证集，H2 |
| FPER | 在有 FM 负例和有效 skill 的 query 上，`max score(FM) > max score(valid)` 的比例 | 验证集，H3 |
| 分数间隔 z | `(max_valid − max_FM) / std(top-100 scores)` | 验证集，H3 |
| rank displacement | `rank(gold) − rank(best FM)` | 验证集，H3 |

FPER 的关键点：不需要重新标注。只要一对 (query, skill) 有了标签，就可以直接算 BM25、Dense、Reranker、SkillSight 对这一对的分数，再看它在全池里的排名。这样可以比较四种方法在同一批 pair 上的行为，标注成本不增加。

### 3.4 统计

- 比例给 Wilson 95% 置信区间。
- 均值给 10,000 次 query-level bootstrap。
- 方法对比用 paired bootstrap，按 query 重采样，不按 pair。
- 标注一致性用 Cohen's κ，给 bootstrap 置信区间。
- 主指标只有 R@10 和 `P(FM | fail)` 两个。其余为次要指标，多重比较用 Holm 校正，报告未校正和校正后的 p 值。
- 所有阈值在 W3 冻结，不允许看完结果再改。

### E0 复现校验（W1–W2）

做法：

通过标准（G0）：Dense R@10 在 66.09 ± 0.5pp，SkillSight 在 86.13 ± 0.5pp。这里的 66.09 是 4090 上 32k 上下文的结果，V100 上用 8k 截断，允许 ±0.5pp 的出入；超过就要先查清是截断还是数值问题，不能直接进入标注。

2026-11-20 已完成：Dense 66.04（-0.05），SkillSight 86.07（-0.06），G0 通过。

### E1 基线（W2）

| 编号 | 方法 | 实现 | 说明 |
|---|---|---|---|
| B1 | BM25 | `bm25s` 或 `rank_bm25`，英文小写 + 停用词 | 纯词法基线 |
| B2 | Dense | Qwen3-Emb-0.6B，现有代码 | 主基线 |
| B3 | Dense + Reranker | Dense top-100 → `BAAI/bge-reranker-v2-m3` → top-K | 交叉编码器重排 |
| B4 | SkillSight | 现有代码，`candidate_k=300` | 当前最强免训练基线 |

B3 在 V100 上按 FP16 跑，5,400 × top-100 约 54 万对，预计 2–4 小时，放 overnight。BM25 用 20 核 CPU，几分钟。

2026-11-20 已完成的 E1 结果（R@10，micro）：

| 任务 | BM25 | Dense | SkillSight | Dense+Reranker |
|---|---:|---:|---:|---:|
| theoremqa | 85.81 | 94.78 | 96.12 | 91.03 |
| logicbench | 26.84 | 35.39 | 69.21 | 20.53 |
| toolqa | **80.56** | 50.21 | 91.54 | 72.03 |
| medcalcbench | 63.18 | **99.36** | 99.00 | 50.91 |
| champ | 45.98 | 62.94 | 58.98 | 42.77 |
| bigcodebench | 58.21 | 55.94 | 76.68 | 35.70 |
| **总体** | **64.04** | **66.04** | **86.07** | **54.23** |

总体看 BM25 只比 Dense 低 2pp，但分任务完全不是一回事：BM25 在 toolqa 上高 30.35pp，Dense 在 medcalcbench 上高 36.18pp。这说明两件事：

1. 不能只拿一个 retriever 的失败集代表“现有方法的失败”。BM25 的失败集中在 medcalcbench 和 logicbench，Dense 的失败集中在 toolqa 和 logicbench，两者的失败构成不同。
2. 后面做 FM 占比时，至少要对 Dense 和 BM25 各算一次，主表用 Dense，BM25 作为对照。如果两者 FM 占比差很多，说明 FM 和 retriever 的类型强相关，不能写成“现有方法普遍存在”。

Reranker 是一个明确的负结果：总体 54.23，比 Dense 低 11.81pp，除 toolqa（+21.82）外所有任务都掉，medcalcbench 掉 48.45pp。排查过不是脚本 bug：分数形状 `(100,)`、无 NaN、sigmoid 概率在 0–0.7；512 和 2048 都试过，2048 在抽查的 5 条 medcalcbench 上反而更差。判断是通用 cross-encoder 更偏向词面和段落匹配，对“这篇文档是否包含所需计算步骤”不敏感，和 ToolRet 里 MonoT5 重排掉点的结论一致。E1 的主基线仍然是 Dense 和 SkillSight，Reranker 作为负结果保留，不进入后续主方法。

E1 的附加诊断，不占额外标注：

- **D1 oracle 任务过滤**：只保留 gold 所属任务族的候选，算 R@10 上界。
- **D2 top-5 同任务占比**：每个 query 的 top-5 里有多少来自 gold 任务族。用来判断失败是跨域还是域内。
- **D3 gold 深度**：gold 在 top-10 / top-100 的比例，复用已复现的 86.39% 深度召回结果。

产出：`E1_baselines.csv`、`E1_diagnostics.csv`、分任务表。

注意：ToolRet 的经验是通用重排可能有害。如果 bge-reranker 在这份数据上掉点，如实报告，不换模型凑结果。

### E2 Pilot 失败分析（W4–W6）

- 100 条 query × top-5 = 500 对，全部人工标注。
- 120 对做第二人独立标注，算 κ。
- 7 天后自复查 100 对，算 intra-annotator agreement。
- 产出分类分布、κ、10 个典型案例。

这一阶段只回答“分类能不能稳定复现”，不急着下“FM 很多”的结论。

### E3 验证（W7–W10）

- 200 条 query × top-5 = 1,000 对。
- 流程：Qwen3-4B 按固定 prompt 预标 → 人工逐条确认或改写 → 100 对第二人复核。
- 预标只用于减少翻正文的时间，最终标签以人工为准。
- 产出 `P(FM | fail)`、回加权 `P(FM)`、分任务与同域/跨域拆分、FVA rate、adjusted R@K。

### E4 Hard-negative 诊断（W11）

从验证集里挑出同时有有效 skill 和 FM 负例的 query，构成四类候选：

1. 有效：gold 或 FVA。
2. FM 负例：semantic=2、coverage=0，取 Dense 排名最高的一个。
3. 通用负例：与 query 共享主题词、但正文以模板为主，取自 pilot 中标为 generic 的技能。
4. 随机负例：从全池随机抽一个。

对每个候选算 BM25、Dense、Reranker、SkillSight 分数，报告：

- pairwise accuracy：有效 skill 分数高于负例的比例，分负例类型。
- 分数间隔 z。
- FPER。
- 同域与跨域分开报。

这一组不需要新标注，是 Gate 3 的主要证据。

### E5 功能证据重排（W12–W16，条件执行）

只在 G2、G3 通过后做。

功能字段抽取两条路线：

| 编号 | 做法 | 成本 | 用途 |
|---|---|---|---|
| F1 | 只用 `description` | 零 | 对照，验证“描述不够” |
| F2 | 规则抽取：Markdown 标题中含 formula / steps / when to use / input / output 的段落，加公式行、首句 | 低 | 主方案 |
| F3 | Qwen3-4B 固定 prompt 抽取 `{action, object, constraint, output, condition}`，只对候选并集做 | 中 | 上限对照 |

打分与融合：

```
s_base = Dense 或 SkillSight 分数
s_func = cos(E(q_cap), E(skill_cap)) 或 BM25(q_cap, skill_cap)
s_final = zscore(s_base) + λ · zscore(s_func)
```

λ 在 Dev-B 的 120 条上选，候选 `{0.1, 0.2, 0.5, 1.0}`。选完冻结，再到 80 条 held-out 和 5,100 条 test 上评。

对照组必须有：

- 随机功能文本（把技能的功能字段随机打乱）。
- 等长随机文本。
- 只用长度特征。
- 只用 description。
- 任务质心先验（query 到 6 个任务质心的相似度），用来检验功能证据是否只是域先验。

主表至少包含：Dense、Dense+Reranker、SkillSight、SkillSight+F2、SkillSight+F3、BM25+F2。报告 R@10、R@5、nDCG@10、FPER、FM-hard 子集增益。

### E6 泛化（W17）

- 分任务报 ΔR@10，看增益是否集中在某几个任务。
- SkillBench-Supp 75 任务做外部流程验证，只报 R@10，不做占比估计（75 条 query 不够）。
- SkillRet 6,660 子池作为可选，只有在 W1 就能下载成功且 G4 通过时才做。

### E7 Agent 端到端（W18，默认不做）

V100 根分区只剩 9.1G，放不下 Qwen3-4B 的 8G 权重；服务器也没有 vLLM。默认删掉这条实验。如果后面必须补，改用 4-bit 量化或换一台有 4090/ A100 的机器，单独评估，不纳入主计划。

## 5. 标注协议

> 单人工 + 4 个 LLM 预标的完整方案见 `03_LLM标注方案.md`。人工是唯一参考标签，LLM 只做预标、triage 和对照；不写 inter-annotator agreement。

### 5.1 两级标签

Pair 级，每条 query–skill 一对：

| 字段 | 取值 | 说明 |
|---|---|---|
| `semantic` | 0 / 1 / 2 | 0 无关；1 弱相关，同领域但不同问题；2 强相关，主题和对象都对得上 |
| `coverage` | 0 / 1 / 2 | 0 不能完成；1 只能完成部分必要步骤；2 能完成全部必要步骤 |
| `judgment` | Gold / FVA / Invalid | Gold 是数据集标注；FVA 是功能等价的替代；Invalid 是其余 |
| `invalid_reason` | generic / topic_related / unrelated / duplicate | 只在 Invalid 时填 |
| `same_task_family` | yes / no | 自动填，retrieved skill 与 gold 是否同一任务前缀 |
| `gold_issue` | yes / no | gold 自身 coverage < 2 时记 yes，单独统计，不混入 FM |
| `evidence` | 原文一句 | 支持 coverage 判断的技能原文，必须能定位 |
| `confidence` | 1 / 2 / 3 | 1 不确定，3 确定 |

Query 级，每条 query 一行：

| 字段 | 取值 | 说明 |
|---|---|---|
| `outcome` | solved / solved_by_alternative / failed | solved 指 gold 在 top-5；solved_by_alternative 指没有 gold 但有 FVA |
| `cause` | FM / generic / retrieval_gap / multi_skill / long_doc / other | 只对 failed 填 |
| `ambiguous` | yes / no | query 是否存在另一种合理解读，若有，写出该解读 |
| `required_skills` | 文本 | multi_skill 时列出需要的 2 个以上能力 |
| `gold_rank_dense` | 整数 | 自动填 |
| `same_task_share_top5` | 0–5 | 自动填 |

### 5.2 Pair 级判定顺序

1. 读 query，写出必要功能需求。通常 1–3 条，格式是“动作 + 对象 + 输出/约束”。
2. 判 `semantic`。只看主题和对象，不看能不能做。
3. 判 `coverage`。逐条需求在技能正文里找证据，找不到就记为 0。不要因为“看起来像”给 2。
4. 定 `judgment`：
   - 是 gold，记 Gold。gold 也要判 coverage，若 coverage < 2，记 `gold_issue=yes`，单独统计，不算 FM。
   - 不是 gold，但覆盖全部必要需求，且不需要额外技能，记 FVA。
   - 其余记 Invalid。
5. Invalid 再定 `invalid_reason`：
   - 正文以模板、使用说明、通用建议为主，没有针对该任务的具体方法，记 generic。
   - 主题相关、但缺关键步骤或方法不对，记 topic_related。
   - 主题也不对，记 unrelated。
   - 与另一个技能几乎重复但细节冲突，记 duplicate。

Functional Mismatch 的操作化定义：

```
FM = Invalid ∧ semantic = 2 ∧ coverage = 0
Partial FM = Invalid ∧ semantic = 2 ∧ coverage = 1
```

主结果报 strict FM，Partial FM 单独报一列，不混在一起。

### 5.3 Query 级主因判定

只对 `failed` 判，按下面顺序，命中即停：

1. `multi_skill`：完成任务需要两个以上不能由单个技能提供的能力。
2. `FM`：top-5 里至少有一个 semantic=2、coverage=0 的技能，且它排在 gold 之前。
3. `generic`：排名最高的 invalid 技能是 generic，正文主要是模板。
4. `long_doc`：gold 本身相关，但关键功能信息在正文 20% 之后，且 gold 排名 > 20。
5. `retrieval_gap`：top-5 里没有 semantic≥1 的技能，gold 相关但没被召回。若 gold 与 query 的表面词重叠很低，标为词法/表示问题。
6. `other`：以上都不适用，写清理由。

注意：`ambiguous` 不作为失败原因。它描述的是 query 本身有多个合理解读，可能让一个被标成 FVA 的技能变得合理。这个字段单独统计，用来解释 FVA 和标注分歧。`multi_skill` 与 `FM` 可以同时成立，报告时给一张交叉表，不要互相覆盖。

### 5.4 锚点例子

- **FM**：query 问 Lah number（把 8 个元素分成 5 个非空有序子集），gold 是 `theoremqa_000 Lah Numbers`，检索到 `theoremqa_241 Stirling Numbers of the Second Kind`。主题都是组合计数，但后者数的是无序子集，方法不对。semantic=2，coverage=0，judgment=Invalid，reason=topic_related。
- **FVA**：query 问“帮我找一个能做 X 的技能”，gold 是 `web_00000 find-skills`，检索到 `web_01099 find-skills`。两者描述完全相同，功能等价，不是 gold 但不应算失败。
- **Generic**：检索到的技能正文大段是“Use this skill when…”“Follow these steps…”，没有任何针对该 query 对象的公式或操作，记 generic。
- **Partial FM（构造示例）**：query 要“按月份汇总销售额并生成 Excel”，技能只能做汇总，不能导出 Excel，coverage=1。
- **重复技能**：query 与 `skill-creator` 相关，池里有 85 个同名变体。如果其中一个能完成需求，记 FVA，不因为不是 gold 就记错。

### 5.5 边界规则

- FVA 必须覆盖全部必要需求，部分覆盖不算。
- 只提供背景知识、不提供可执行方法的技能，不算覆盖“计算/生成/转换”类需求。
- 需要外部 API、付费服务或未提供凭据的技能，按当前环境不能完成处理，记 coverage=0，并在备注里说明。
- 多技能 query 里，单个技能只有覆盖全部需求才算 FVA。
- 近似重复的技能，只要功能等价就算 FVA，不要求文本相似。
- 不能因为技能里出现了 query 的答案就判为可完成；要看它是否给出方法。
- 不确定时记 confidence=1，并在备注写清犹豫点，留给裁决，不要猜。

### 5.6 质量控制

- 校准：先标 30 对，自己按手册走一遍，记录犹豫点，修手册，冻结 v1。
- 盲标：表格不显示 retriever、rank、score、gold 身份。先看 query 和参考答案，判完再看 gold。
- 单人方案：本项目只有一名人工标注者。不再使用“双人独立标注 + Cohen's κ”的表述，改为：
  - 人工 7 天后自复查 100 对，报告 intra-annotator agreement；
  - DeepSeek、Qwen、智谱、OpenAI 四个模型独立预标，报告 LLM–human agreement（按类别给 precision / recall / F1）；
  - 四个模型多数票（≥3 一致）作为预标，2–2 平票和所有 FM/FVA 候选交人工确认；
  - 论文里写“single human annotator with LLM-assisted pre-annotation and audit”，不写“inter-annotator agreement”。
- 审计：pilot 500 对全部人工确认；validation 1,000 对人工确认全部 FM/FVA 候选，再随机抽 20% 确认其余标签。审计通过后，剩余标签才可用模型预标结果。
- 裁决：人工确认的标签为最终标签，模型输出只作为预标和对照，不改写人工判断。
- 所有原始表只追加不覆盖，版本号写在文件名里，模型原始输出单独保存。

### 5.7 标注成本

| 阶段 | 对数 | 单对时间 | 人工时间 | 说明 |
|---|---:|---:|---:|---|
| 校准 | 30 | 90 s | 0.8 h | 自己标，记录犹豫点 |
| Pilot | 500 | 40–60 s（有 LLM 预标） | 6–8 h | 全部人工确认 |
| Validation | 1,000 | 30–45 s（有 LLM 预标） | 6–9 h | 全部 FM/FVA + 20% 随机审计 |
| 合计 | 1,530 | | 13–18 h | 不含模型调用等待 |

按 4 周摊开，每周 3–5 小时。如果 W9 结束时 validation 还没过半，把 200 条降到 160 条（128 失败 + 32 成功），不要拖到 W11。

## 6. Gate 与止损

| Gate | 时点 | 指标 | 通过线 | 通过后 | 未通过 |
|---|---|---|---|---|---|
| G0 | W2 | 复现偏差 | Dense 与 SkillSight 均在 ±0.5pp | 进入 E1 | 修环境，不进标注 |
| G1 | W6 | 标注可靠性 | 人工 7 天自复查 κ ≥ 0.70；四模型多数票对人工的 FM F1 ≥ 0.75，FVA recall ≥ 0.70 | 冻结手册 | 改 prompt/手册；仍不达标就降级为 AI triage，人工标全量 |
| G2 | W10 | FM 占比 | `P(FM \| fail)` ≥ 25%，95% 下限 ≥ 15% | 进入方法设计 | <10% 走 Stop A；10–25% 降为次要章节 |
| G3 | W11 | 可区分性 | Dense FPER ≥ 25%，最强基线 ≥ 15% | 进入 E5 | 全部 <10%，停方法，转测量/FVA 论文 |
| G4 | W16 | 方法效果 | 功能分数 pairwise ≥ 65%；R@10 ≥ +2.0pp 且 CI 不含 0；控制特征 ≤ +0.5pp | 写方法章 | 只报诊断与阴性结果 |

G1 如果两轮后仍低于 0.50，退化为二分类：只判“有效 / 无效”，FM 作为无效里的一个子类，不再要求 6 类主因。

G2 必须同时看同域与跨域：

- 如果 oracle 任务过滤增益 ≥ 20pp，且 FM 主要来自跨域，论文口径改成“跨域路由 + 域内功能匹配”，方法里必须有域先验对照。
- 如果 FM 主要来自同域（例如 Lah vs Stirling），功能建模的方向成立，可以按原计划推进。

Stop Rule A（FM 很少）：论文改为 **Skill Retrieval Failure Analysis + Single-gold Measurement**。主线变成 H1：单 gold 低估了多少、FVA 有多普遍、哪些失败其实是标注问题。这个方向有 ToolEX 和 SkillRet 的外部证据支持，不依赖 FM。

Stop Rule B（FM 多但 κ 低）：先改定义，把 FM 收缩成“主题强相关且缺一个明确必要步骤”，用更小的判定单元重标 50 对，不急着做方法。

Stop Rule C（全部通过）：进入 E5，方法限定为免训练重排。

## 11. 与 v2.0 的差异

1. 数据集从“待定”固定为 SRA-Bench，SkillRet 与 SkillBench 只做外部验证。理由是本地已有数据，且 5,400 条 query 足够做分层抽样。
2. 标注从一套 7 类改成两级：pair 级判语义与覆盖，query 级判主因。原来的 Semantic Ambiguity 改成 query 标记，不再和失败原因混在一起。
3. 把 Functionally Valid Alternative 从“不计为失败”改成可测量的主结果之一，增加 adjusted R@K 和 FVA rate。SRA-Bench 里 2,206 组同名技能说明这个问题不是假设。
4. Stop Rule 从文字描述改成带阈值的 Gate，G1–G4 各有通过线和未通过动作。
5. 固定 Dev-A、Dev-B、Test 三段划分，pilot 只用于建分类和手册，不用于报方法效果。
6. 方法阶段限定为免训练重排，必须带随机文本、等长文本、长度、description、任务先验五类对照。
7. 新增跨域混淆诊断。如果失败主要来自任务路由，FM 的结论必须限定在同域内部，否则会把域不匹配写成功能不匹配。

## 附录 A 抽样与回加权的实现要点

- 抽样前先保存全量 Dense 的 `query_id, task, hit@5, gold_rank`，不要边跑边抽。
- 每个任务内部分别抽失败与成功，不要先全局抽再分层，否则小任务会缺样本。
- 回加权时用任务真实失败率，不用样本失败率。
- 报告 `P(FM | fail)` 时给未加权和按任务加权两个数，差异大说明任务间异质。
- 所有 bootstrap 按 query 重采样，pair 级指标先聚合到 query 再重采样，避免把同一 query 的 5 对当成独立样本。
