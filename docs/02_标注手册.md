# 标注手册 v1.0

> 配套文件：`标注/annotation_pilot.xlsx`（500 对，100 条 query）、`标注/annotation_pilot_key.csv`（分析用，标注时不要打开）。
> 制定日期：2026-11-20。正式开标前先做 30 对校准，校准后冻结本手册。

---

## 1. 这份手册要解决什么

判断一个被检索到的 skill 对当前 query 是不是**真的有用**，并把失败原因归到一个可复现的类别里。重点不是“这个 skill 讲的是不是同一个主题”，而是“它能不能完成 query 要求的事”。

标注单位有两级：

- **Pair 级**：一条 query 配一个 retrieved skill，判语义相关、功能覆盖、是否等价替代。
- **Query 级**：一条 query 判整体结果，是解决、被替代解决，还是失败；失败再判主因。

---

## 2. 文件与角色

| 文件 | 谁看 | 内容 |
|---|---|---|
| `annotation_pilot.xlsx` | 标注者 | query、参考答案、skill 名/描述/正文片段，以及待填字段 |
| `annotation_pilot_key.csv` | 分析者 | pair_id 对应的 skill_id、gold、Dense 排名、分数。**标注时不要打开** |
| `pilot_sample.csv` | 分析者 | 抽样清单与分层信息 |

Excel 里每个 `q_block` 是一组，同一个 query 下有 5 个 skill（A–E），顺序已经打乱。`pair_id` 形如 `Q001C`，只用于对齐，不透露排名。

`Gold / FVA / Invalid` 三个判断都**不要看 key 文件**。先按 query 和 skill 正文独立判断，判完再由脚本合并 gold 信息。

---

## 3. 开始前的准备

1. 打开 `annotation_pilot.xlsx`，不要打开 key。
2. 先读第 4、5 节的规则，再用 30 对做校准。
3. 每条 query 先看 `query` 和 `reference_answer`，再看 5 个 skill。
4. 判断时只看 `skill_name`、`skill_description`、`skill_snippet`。片段不够时，按 `pair_id` 到 key 里找 `skill_id`，再回语料查全文。这一步只在片段明显不足时做，并在 `notes` 里写“查了全文”。
5. 不要根据 skill 名的前缀猜任务；名字里的任务前缀在导出时已经保留，但不要用它代替功能判断。

## 4. Pair 级判定

### 4.1 先写必要功能需求

用一句话列出 query 真正要求的东西，格式是“动作 + 对象 + 输出/约束”。通常 1–3 条。

例子：

```text
Query: How many ways are there to divide a set of 8 elements into 5 non-empty ordered subsets?

必要需求:
1. 计算组合数
2. 对象是“8 个元素分成 5 个非空子集”
3. 约束是“有序”，不是无序
4. 输出是一个整数
```

这一步写在草稿或 `notes` 里。后面的 coverage 就是逐条对照。

### 4.2 semantic（0 / 1 / 2）

只看主题和对象，不看能不能做。

| 取值 | 含义 | 例子 |
|---|---|---|
| 0 | 无关 | query 问组合计数，skill 讲 CSS 布局 |
| 1 | 弱相关，同领域但不同问题 | query 问 Lah 数，skill 讲一般排列组合 |
| 2 | 强相关，主题和对象都对得上 | query 问 Lah 数，skill 讲 Stirling 数；都在讲“把集合划分成子集” |

### 4.3 coverage（0 / 1 / 2）

逐条必要需求，在技能正文里找证据。找不到就记 0，不要因为“看起来像”给 2。

| 取值 | 含义 | 判定 |
|---|---|---|
| 0 | 不能完成 | 缺关键步骤、方法不对、只给背景知识 |
| 1 | 只能完成部分必要步骤 | 例如只能汇总不能导出 Excel |
| 2 | 能完成全部必要步骤 | 有明确方法、公式、步骤或 API，且不需要额外技能 |

### 4.4 judgment（Gold / FVA / Invalid）

| 取值 | 条件 |
|---|---|
| Gold | 这个 skill 就是数据集标注的 gold |
| FVA | 不是 gold，但 coverage=2，且不需要额外技能 |
| Invalid | 其余 |

注意：gold 也要判 coverage。如果 gold 自己 coverage < 2，仍然记 Gold，但在 `notes` 写“gold 自身不满足”，分析时单独统计，不混进 FM。

### 4.5 invalid_reason（只在 Invalid 时填）

| 取值 | 条件 |
|---|---|
| generic | 正文以模板、使用说明、通用建议为主，没有针对该任务的具体方法 |
| topic_related | 主题相关，但缺关键步骤或方法不对 |
| unrelated | 主题也不对 |
| duplicate | 与另一个技能几乎重复但细节冲突，或同一技能的多个变体互相矛盾 |

### 4.6 evidence 与 confidence

- `evidence` 抄一句能支持 coverage 判断的原文，必须能在 skill 里定位。判 coverage=0 时，抄一句“它实际在讲什么”的原文，或者写“全文无相关步骤”。
- `confidence`：1 不确定，2 一般，3 确定。不确定的留给裁决，不要猜。

## 5. Query 级判定

只对 `failed` 的 query 判主因。`solved` 和 `solved_by_alternative` 只填 outcome。

### 5.1 outcome

| 取值 | 条件 |
|---|---|
| solved | gold 在 top-5 |
| solved_by_alternative | 没有 gold，但 top-5 里有 FVA |
| failed | top-5 里既没有 gold，也没有 FVA |

### 5.2 cause（按顺序，命中即停）

1. `multi_skill`：完成任务需要两个以上不能由单个技能提供的能力。
2. `FM`：top-5 里至少有一个 semantic=2、coverage=0 的技能，且它排在 gold 之前。
3. `generic`：排名最高的 invalid 技能是 generic，正文主要是模板。
4. `long_doc`：gold 本身相关，但关键功能信息在正文 20% 之后，且 gold 排名 > 20。
5. `retrieval_gap`：top-5 里没有 semantic≥1 的技能，gold 相关但没被召回。
6. `other`：以上都不适用，写清理由。

`multi_skill` 和 `FM` 可以同时成立，报告时给交叉表，不要互相覆盖。

### 5.3 ambiguous

query 是否存在另一种合理解读。若有，写出该解读。这个字段不作为失败原因，只用来解释 FVA 和标注分歧。

## 6. 锚点例子

### 6.1 Functional Mismatch

```text
Query: How many ways are there to divide a set of 8 elements into 5 non-empty ordered subsets?
Gold: theoremqa_000 Lah Numbers
Retrieved: theoremqa_241 Stirling Numbers of the Second Kind
```

两者都在讲“把集合划分成子集”，semantic=2。但 Stirling 数数的是**无序**子集，Lah 数数的是**有序**列表，方法不对，coverage=0。judgment=Invalid，invalid_reason=topic_related。

### 6.2 Functionally Valid Alternative

```text
Query: 帮我找一个能做 X 的技能
Gold: web_00000 find-skills
Retrieved: web_01099 find-skills
```

两者描述完全相同，功能等价，skill_id 不同。judgment=FVA，不算失败。

### 6.3 Generic

检索到的技能正文大段是“Use this skill when…”“Follow these steps…”，没有任何针对 query 对象的公式、步骤或 API。semantic 可能是 1 或 2，coverage=0，invalid_reason=generic。

### 6.4 Partial FM

query 要“按月份汇总销售额并生成 Excel”，技能只能做汇总，不能导出 Excel。semantic=2，coverage=1，judgment=Invalid，单独记为 Partial FM，不并入 strict FM。

### 6.5 重复技能

query 与 `skill-creator` 相关，池里有 85 个同名变体。其中一个能完成需求，就记 FVA；不能完成，按实际 coverage 判 Invalid，不因为“不是 gold”就自动记错。

## 7. 边界规则

- FVA 必须覆盖全部必要需求，部分覆盖不算。
- 只提供背景知识、不提供可执行方法的技能，不算覆盖“计算/生成/转换”类需求。
- 需要外部 API、付费服务或未提供凭据的技能，按当前环境不能完成处理，coverage=0，并在 `notes` 说明。
- 多技能 query 里，单个技能只有覆盖全部需求才算 FVA。
- 近似重复的技能，只要功能等价就算 FVA，不要求文本相似。
- 不能因为技能里出现了 query 的答案就判为可完成；要看它是否给出方法。
- 引用类技能只给“去哪里找”，不给具体答案，按 coverage=0 或 1 处理，看它是否覆盖了必要步骤。
- 不确定时记 confidence=1，在 `notes` 写清犹豫点，留给裁决。

## 8. 常见错误

| 错误 | 纠正 |
|---|---|
| 把“主题相关”直接当成“能用” | semantic 和 coverage 分开判 |
| 看到公式就认为能算 | 检查公式的对象和约束是否与 query 一致 |
| 因为不是 gold 就判失败 | 先判是不是 FVA |
| 因为 top-5 里有 gold 就认为 query 成功 | gold 自身也可能 coverage < 2，记 gold_issue |
| 把多技能 query 硬塞给一个技能 | 单个技能必须覆盖全部需求才算 FVA |
| 用 key 里的排名推断哪个是 gold | 标注时不要打开 key |

## 9. 质量控制

- 校准：先标 30 对，两人讨论，修手册，冻结 v1。
- 盲标：不看 retriever、rank、score、gold 身份。
- 双标：pilot 120 对、validation 100 对由第二人独立标注。κ 在裁决前计算。
- 裁决：分歧逐条讨论，记录最终标签和理由，不改原始记录。
- 自复查：7 天后随机抽 100 对重标，算 intra-annotator agreement。
- 所有原始表只追加不覆盖，版本号写在文件名里。

## 10. 一页速查

```text
semantic: 0 无关 / 1 同领域不同问题 / 2 主题和对象都对
coverage: 0 不能做 / 1 只能做一部分 / 2 全部能做
judgment: Gold / FVA / Invalid
invalid_reason: generic / topic_related / unrelated / duplicate

FM       = Invalid + semantic=2 + coverage=0
Partial  = Invalid + semantic=2 + coverage=1
FVA      = 非 Gold + coverage=2 + 不需要额外技能

query cause 顺序: multi_skill → FM → generic → long_doc → retrieval_gap → other
ambiguous 只做标记，不做失败原因
```
